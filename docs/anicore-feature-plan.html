01 / Start from what exists

A strong engine; room for a better workspace

Already implemented

  • Catalogue search, sorting, season/year/status/format filters, detail views and language evidence.
  • Selective syncs, durable stage state, retry cooldowns, pause/resume/stop and provider freshness.
  • Revision-based cache invalidation, read isolation, summary projection and ID cursor pagination.
  • Scheduled mapping/language audits, backup creation/verification/restore, proxy and cache controls.

Next opportunity

  • Bring the existing language review API into an authenticated dashboard workflow.
  • Expose dub/sub discovery directly in catalogue filters.
  • Show why a mapping or coverage result is trustworthy, with consistent evidence semantics.
  • Turn stage state and audit reports into actionable operational views.

This is a source review, not a live deployment audit. No production latency, failure rates or catalogue counts were measured.

Keep the data contract honest. A confirmed language track does not prove every episode is available. Confidence scores are evidence weights, not probabilities. Unknown remains unknown; language existence does not imply current regional licensing.

04 / Implementation briefs

Buildable scope and acceptance criteria

Endpoint names marked “proposed” require implementation. Source paths refer to the repository baseline reviewed for this plan.

01 / Language review workspace

P1 · 5–8 days

Outcome: An operator can investigate an uncertain language result and apply a reasoned title-level override without using raw API requests.

  • Reuse: GET /admin/language-status/review-queue, detail language evidence and POST /admin/anime/:id/language-override. The existing queue covers unknown/possible, not all conflicts or likely results.
  • Add: Review view, joined title metadata, total count and filters; a separate admin-token session (the monitor code does not authorize admin routes). Add a durable mutation journal and optimistic version check for stale reviews.
  • First slice: Read-only list → evidence detail → authenticated override form with required reason. Add defer/resolve workflow only with persisted review state; do not hide items silently in the browser.
  • Accept: Unauthorized writes fail; stale edits return a recoverable conflict; overrides survive provider refresh; every override has before/after values and reason; unknown episode coverage stays unknown. Keyboard navigation, empty queue, expired session and failed save are usable.
Implementation locations & dependencies

apps/web/src/lib/views.ts, apps/web/src/app.tsx, a new review view/client; apps/api/src/modules/language-status/; schema/migration for journal and versioning. Define credential handling and audit actor identity before enabling writes. A shared token alone does not identify individual reviewers.

02 / Mapping & coverage inspector

P1 · 3–5 days

Outcome: A detail view explains which provider identity, segment and language evidence produced a result, and where the model abstained.

  • Reuse: Full detail, mappings, segment ranges, evidence links and provider freshness already exposed in the detail view.
  • Add: A focused “Why this result?” panel showing primary identity, mapping provenance, segment offset and canonical-to-provider episode alignment. Return sanitized decision reasons where stored data cannot explain an abstention.
  • Accept: Split seasons, absolute numbering, specials, gaps and ambiguous alignments render correctly. No arbitrary match is suggested as confirmed; unavailable historical diagnostics are labelled unavailable. Confidence never appears as probability.
Implementation locations & dependencies

Extend anime-detail-dialog.tsx and shared detail types; inspect provider-segments.ts and provider alignment modules. Persist structured diagnostics only if existing snapshots are insufficient; bound retained data and keep raw provider payloads private. Reuse the read-only inspector in 01.

03 / Language-aware catalogue

P1 · 4–7 days

Outcome: Find anime with confirmed English audio, Portuguese subtitles or complete known episode coverage directly in the catalogue.

  • Reuse: Catalogue filtering/query serialization and the canonical episode coverage resolver.
  • Add: Proposed optional languageCode, mediaType, languageStatus and coverage filters on GET /anime; optional summary columns with clear status and available/missing/unknown counts.
  • Semantics: “Complete known coverage” needs a reliable nonzero expected episode denominator, every canonical episode available, and no unresolved expected episodes. A partial local episode list cannot establish completeness. Track existence and freshness remain separate filters/concepts.
  • Accept: List membership matches the detail resolver for conflicting evidence and overrides; absent evidence stays unknown; counts/sorts/pagination agree for both pagination modes; default response contracts remain compatible. Benchmark SQL under sync load and avoid one query per row.
Implementation locations & dependencies

anime-toolbar.tsx, anime-query.ts, catalogue API types, anime routes/service and coverage resolver. Spike a shared SQL-compatible resolved coverage projection or a revision-maintained aggregate before committing to query shape. Add indexes only after query-plan measurements.

04 / Saved views & shareable details

P2 · 2–3 days

Outcome: Bookmark a catalogue query, reopen an exact detail and return to the same filters.

  • Reuse: Existing hash navigation and catalogue query state.
  • Add: Versioned query/deep-link format, named local presets, URL-driven anime detail selection, copy-link action and browser back/forward handling. Build existing-filter support independently; add 03’s parameters later.
  • Accept: Reload restores filters and selected title; back closes detail and restores the previous view; malformed links fall back safely; removed titles show a useful 404 state; links/presets never contain tokens. Gracefully handle unavailable local storage.
Implementation locations & dependencies

views.ts, use-dashboard-view.ts, anime-query.ts, catalogue/detail hooks and storage helpers. Update route parsing deliberately: it currently recognizes four dashboard paths. Local presets do not imply account synchronization.

05 / Targeted recovery jobs

P2 · 7–12 days

Outcome: Retry eligible failed stages for a selected title set without reconciling the full catalogue.

  • Reuse: Durable stage success/failure/freshness state, retry cooldowns, checkpoint rules, bounded fetch windows and database lease.
  • Add: A bounded title/stage selection in the sync runner, authenticated preview/start endpoints (proposed), durable job ID/status and idempotent start keys. Validate supported stages and dependencies on the server.
  • Accept: Fresh dependent successes are reused; cooldowns remain enforced by default; duplicate submissions produce one job; concurrent jobs cannot bypass lease ownership; interrupted work can resume. Optional-provider warnings remain distinct from required failures. Existing full-run checkpoints are preserved.
Implementation locations & dependencies

apps/api/src/lib/sync-process.ts, sync CLI/runner, packages/providers/src/lib/stage-state.ts, sync monitor routes/types/client and a recovery view. Reuse monitor authorization for sync control; admin authority remains required for metadata mutations. Build a durable minimal job/run record before the dashboard Start action.

06 / Run history & provider health

P2 · 5–8 days

Outcome: Compare runs and distinguish rate limiting, cache reuse, optional warnings and hard failures.

  • Reuse: Current monitor progress/events and local performance instrumentation. The bounded rotating log tail is not a complete run-history store.
  • Add: Durable bounded run summaries (scope, start/end, outcome and stage counts), provider error categories, last-success timestamps and known cooldown deadlines. Add authenticated summary reads; aggregate asynchronously with a configurable retention policy.
  • Accept: Totals reconcile with run outcomes; interruption and restart do not erase history; missing telemetry displays “not recorded”; secrets and upstream response bodies never enter summaries. Durations remain explicitly local diagnostics. ETA appears only with enough recent comparable samples.
Implementation locations & dependencies

Sync engine/monitor events, performance module, new run summary schema/service and monitor dashboard. Share the minimal durable run record with 05; historical analytics can follow targeted recovery. Start with fixed local retention (for example 90 days), subject to storage measurement.

07 / Audit & backup centre

P2 · 5–9 days

Outcome: See the latest integrity findings and verification status, then create a managed backup from the dashboard.

  • Reuse: Scheduled read-only audits, persisted latest report, and existing create/verify/restore tooling.
  • Add: An authenticated report/backup inventory (proposed), staleness labels, bounded backup jobs and optional schedule/retention settings. Backup names resolve inside a managed directory; the browser cannot supply arbitrary filesystem paths.
  • First slice: Read-only audit report + backup verification inventory. Add create/verify jobs next; keep restore as an explicit operator procedure that creates a new file and requires service stop/switch.
  • Accept: Findings never trigger automatic repair; previous reports survive failures; corrupt backups show failed verification; insufficient disk and active maintenance states are clear. Retention deletes only recognized completed managed backups and preserves the newest verified one. Offsite copies/encryption require separate operational policy.
Implementation locations & dependencies

audit-scheduler.ts, database-backup.ts, backup worker/scripts, new admin operations routes and Data & Cache view. Add retention only after inventory metadata and safe path validation exist. Display actual completion time rather than treating a scheduled attempt as success.

08 / API integration lab

P3 · 3–5 days

Outcome: Developers can understand real AniCore response contracts and try common public reads from the dashboard.

  • Reuse: Existing interactive OpenAPI docs at /docs and schema at /docs/json. Avoid building another general-purpose Swagger interface.
  • Add: Guided examples for provider lookup, summary projection, language resolution and cursor traversal; generated curl snippets; explicit response-header explanation and bounded response preview.
  • Accept: Copyable examples work against the configured API origin; show X-Total-Count and X-Next-Cursor; explain ID-sort/offset restrictions and changing catalogue snapshots. Try actions issue GET requests only; show deadlines and meaningful 400/404 failures. Never copy stored credentials into snippets.
Implementation locations & dependencies

New help/lab view, existing API clients and generated OpenAPI contract examples. No production write playground in the first version. Verify cross-origin header exposure rather than assuming browser access.

05 / Definition of done

Validate contracts, semantics and real usability

Engineering gates

  1. Targeted integration cases for authorization, stale writes, override preservation and coverage resolution on temporary databases.
  2. Catalogue membership/count/cursor regression checks and representative query-plan/load measurements for new filters.
  3. Job restart, duplicate submission, cooldown, single-lease and checkpoint tests before recovery launches.
  4. Run repository lint, typecheck, relevant tests and production build for implemented features; follow installed Turbo documentation before changing its configuration or commands.

Product gates

  1. Keyboard and mobile review of queue, evidence, filter and job workflows.
  2. Loading, empty, stale, unauthorized, partial-result and conflict states have clear recovery actions.
  3. New screen counts come from real APIs; sample fixtures are confined to development/mockups.
  4. Measure review completion time, query latency during sync, recovery success and storage growth after rollout. Set numeric targets from a baseline, not invented results.
Deferred deliberately: New providers, recommendation algorithms, a streaming player and multi-user RBAC. Establish trusted data and usable operations first. Regional availability needs a separate data contract; current primary-language evidence cannot answer licensing questions.
